# 原神养成规划器 Roadmap

状态：正式规划，纳入版本控制并持续维护。本文是当前唯一有效的长期规划；已推翻的旧原型不再保留，避免实现时引用错误方案。

## 产品方向

从分别计算角色天赋素材或武器突破素材的工具，演进为围绕角色、天赋和武器的完整养成规划器。它应能计算完整需求、结合库存分配材料、展示开放日，并在资料可信时估算体力与刷取次数。

v1.x.x 只面向 Windows，以绿色 ZIP 交付。macOS、Linux、OCR、跨设备同步和移动端不阻塞 v1.x.x 核心闭环。

## 已确认原则

1. 离线优先。日常计算、库存和计划不依赖网络；资料更新由用户主动触发。
2. 每个游戏账号内，每种材料只记录一份全局实际库存。系统按该账号中用户可见的计划优先级分配可用数量；分配只用于计算，不扣减实际库存，同一份库存不能同时分给多个计划。
3. 一个培养计划可以包含角色等级与突破、天赋和任意武器目标。用户可以只培养角色、只培养武器或组合多个目标，武器不是角色计划的必填项。
4. 每个培养目标展示自身材料需求，计划总览合并展示该计划全部目标的材料需求；两处必须调用同一套计算规则并保持结果一致。
5. 需求是确定值，掉落是概率模型。期望、保守值和数据来源必须分开说明，不能把期望当保证。
6. 计算功能只能使用已经完成建模和校验的游戏资料。材料 ID、分类、来源、开放状态、合成与转换规则缺失时，界面应明确显示资料缺失，不能按数量为零继续计算。
7. 关闭界面标签只关闭工作区，不删除计划、不改变计划状态，也不释放库存预留。
8. 用户未添加的培养目标不计入需求和完成度，也不显示为空缺或警告。
9. 操作层级最多为全局工作区、培养计划和对象详情查看器三级；对象详情中的补充内容在当前查看器内展开。
10. 每个对外版本都必须独立可用并通过该版本的完整验收；尚未形成闭环的功能不提供正式入口。
11. 用户填写过的新建计划在意外中断后可以恢复最近一次进度；恢复机制不作为独立功能展示。已创建计划继续使用明确的保存和未保存提示。
12. 关键操作应容易发现，同时保留用户决定执行时机的余地。条件满足后显示清晰入口，不使用弹窗、通知或自动状态变更催促用户；扣减库存、完成计划等业务结果只由用户主动确认触发。

## 官方术语与资料来源

- 用户界面和设计文档使用资料源中的官方名称，例如“角色天赋素材”“武器突破素材”；“天赋书”等玩家口语不作为产品文案。
- Schema v2 设计先建立统一术语表，再确定字段、类型和枚举。术语表记录官方中英文名称、完整代码名称、可读的持久化缩写、语义边界、资料来源及 Schema v1 迁移值。
- TypeScript 声明使用完整英文名称，JSON 枚举使用统一的分词缩写，例如 `CharacterTalentMaterial: 'char-talent-mat'`；具体游戏对象使用资料源提供的稳定数字 ID。
- 角色、武器、材料、分类和本地化名称以 Lunaris 同步资料为准。不得凭记忆或玩家俗称手写产品名称。
- 资料必须记录来源 URL、游戏版本、生成时间和可信状态。未来角色或未开放材料可以进入计划，但必须标明当前不可获取。

## v1.2.x 长期数据模型

- `Profile`：设置、培养计划、全局库存、迁移版本和备份元数据。
- `CultivationPlan`：稳定 ID、名称、优先级、状态、时间信息和可选目标模块列表。
- `PlanCreationRecovery`：内部仅保留一份最近的未完成创建记录，包含当前步骤、已选对象和更新时间；完成、放弃或重新开始后删除。
- `TargetModule`：角色等级与突破、天赋、武器、自定义目标等可扩展模块；v1.2.x 首先启用前三类。
- `Material`：稳定 ID、官方名称、类别、稀有度、来源、开放状态、版本和图标。
- `Recipe`：普通三合一、角色被动、同一周本材料转换及其催化材料。不同规则不能硬塞进同一种算法。
- `Inventory`：v1.2.x 暂时允许计划内填写；v1.3.x 升级为按材料 ID 保存的唯一全局库存。
- 完成度、缺口、合成后可用、预留和预计次数均实时推导，不固化为 Profile 真值。

### v1.2.0 主进程与 IPC 拆分

- `src/main/index.ts` 只保留 Electron 启动编排、窗口创建、协议注册和应用生命周期，不继续承载具体业务 IPC 实现。
- 将用户档案、游戏资料和受限系统能力的 IPC 处理器按职责拆入独立模块；窗口关闭握手单独封装，并由主入口显式注册。
- preload 继续只暴露最小化且类型明确的 `DesktopApi`，IPC 通道名称、参数、返回值和异常由共享类型及集成测试锁定。
- 拆分不得改变现有渲染进程调用方式、用户数据路径、资料回退行为或窗口关闭语义。

## v1.x.x 最终界面原型

本节定义 v2.0.0 前唯一有效的桌面端低保真原型。字符图确认信息结构、入口和状态，不代表像素级视觉稿。

版本原型采用增量继承：`v1.2.x` 及后续版本默认保留 `v1.1.0` 已确认并交付的页面、字段、操作和状态。某一版本只画新增或变化区域时，未重复绘制的内容不得被理解为删除；对应设计文档必须明确列出继承项和有意移除项。游戏资料页持续继承资料版本、来源、精确到秒的更新时间、五项内容数量统计、资料操作、目录入口和精确到分钟的同步记录，除非后续设计明确说明变更。

### 培养计划核心闭环

```text
总览“新建培养计划”或顶栏“+”
  -> 检查最近一次创建恢复
  -> 选择角色或跳过
  -> 选择武器或跳过
  -> 检查同对象计划并确认名称
  -> 完成创建
  -> 培养计划工作台
  -> 设置等级、天赋和库存
  -> 保存
  -> 总览显示进度，库存参与计划分配
  -> 发生材料冲突时进入库存分配顺序
  -> 返回计划继续培养
  -> 从“更多”暂停、完成或归档
  -> 总览和库存同步更新
```

- 流程中的返回操作保留已打开标签和滚动位置；需要离开未保存内容时统一进入保存确认。
- 任一步骤失败都停留在当前上下文并保留输入，成功后只进入箭头指向的下一个可见状态。

### 体力估算（v1.5.x）

体力估算是开放日详情中单个素材的按需展开区，不取代确定性的材料缺口：

```text
+----------------------+----------------------+----------------------+
| 估算口径             | 次数                 | 树脂                 |
+----------------------+----------------------+----------------------+
| 平均期望             | 约 ... 次            | 约 ...               |
| 保守参考             | 约 ... 次            | 约 ...               |
+----------------------+----------------------+----------------------+

数据来源：...  样本量：...  游戏版本：...  更新：...       [查看口径]
```

```text

```

- 估算先扣除库存，再采用当前合成角色的整数计算结果；周本转换只影响其对应周本材料，不能折入秘境素材估算。
- “平均期望”不是完成保证；“保守参考”必须在详细设计中定义统计口径，不能用任意倍率伪造。

- 掉落数据缺少来源、样本量、适用难度或游戏版本时使用不可估算状态，不隐藏确定性的尚缺数量。

- 第一步固定选择角色并提供“不添加角色”，第二步固定选择武器并提供“不添加武器”；选择“不添加”后直接进入下一步，不再询问“首先添加”。
- 角色和武器至少选择一个；两步都选择“不添加”时禁用“完成创建”，并提示至少选择一个培养对象。
- 选择角色后默认建立角色等级与突破、天赋两个目标；选择武器后建立武器升级与突破目标，用户进入工作台后可以移除不需要的目标。
- 重复检测只查询当前游戏账号，并展示匹配计划的名称、状态和相关目标。
- 同一账号只有一个对应角色，因此同角色计划使用强提示。“继续编辑已有计划”是推荐主操作；执行后删除本次创建恢复记录并切换到已有计划。原“下一步”按钮改为“仍然创建一份”，只有用户明确选择后才继续。
- 同名武器可能持有多把，因此只对进行中或已暂停的同武器计划显示弱提示。相关计划整行可进入，同时保留正常的“下一步”或“完成创建”按钮。
- 已完成或已归档的同武器计划属于历史记录，不进入重复提示，也不影响新计划创建。
- 第二步在“完成创建”前显示可直接编辑的计划名称输入框，不增加单独的确认步骤。
- 用户尚未编辑名称时，名称随角色和武器选择自动更新；用户编辑后切换为自定义名称，返回上一步调整对象时继续保留。
- 打开后未产生任何选择时不创建恢复记录；用户完成第一个有效选择后，系统保存最近一次创建进度，并在操作区以低强调状态显示“草稿已保存”。

- 点击关闭、切换工作区或返回时显示提示。“暂时离开”保留恢复记录，“放弃本次创建”删除恢复记录。
- 应用崩溃、电脑关机或进程被结束时使用最近一次成功写入的恢复记录，不依赖退出回调。


- 系统只保留最新一份创建恢复记录；完成创建后立即删除。恢复记录不参与完成度、开放日统计或库存预留。

### 培养计划命名

```text
已选择角色和武器    -> “「神里绫华」培养计划”
```

- 自动名称优先使用角色名称；没有角色时使用武器名称。名称使用当前界面语言中的官方对象名称。

- 创建流程自动填入推荐名称，并在完成创建前提供清晰的编辑入口。用户手动修改后停止自动更新；清空后离开输入框时恢复当前对象对应的推荐名称。
- 自定义名称与现有计划重名时在输入框下提示，并在名称有效前禁用“完成创建”；系统只为自动生成的名称自动追加序号。

- 默认按计划创建时间从早到晚分配材料，先创建的计划先获得可用库存；内部稳定 ID 仅在创建时间完全相同时保证结果确定。
- 用户从库存顶栏的“分配顺序”进入全局排序；拖动后保存为当前账号的自定义顺序，所有共享材料统一采用该顺序。
- 库存顶栏仅在存在缺口冲突时显示“冲突 N”；点击后筛选冲突材料。列表中的冲突数值或背包格的冲突状态可进入该材料的分配详情。
- 材料分配详情中的“调整整体分配顺序”进入同一排序界面，不提供单个材料的特殊优先级。
- 只有进行中计划参与预留。暂停、完成、归档和取消立即释放预留，但不修改实际库存。

### 完成、暂停与归档

计划材料尚未满足时，完成入口位于培养计划工作台顶栏的“更多”菜单：

```text
[已保存] [更多 v]
          +----------------+
          | 重命名         |
          | 另存为         |
          |----------------|
          | 暂停计划       |
          | 标记为完成     |
          | 归档计划       |
          |----------------|
          | 删除计划       |
          +----------------+
```

材料已经满足全部目标时，完成入口提升到顶栏：

```text
[已保存] [完成计划] [更多 v]
```

```text
完成“神里绫华培养”

( ) 按计划需求扣减实际库存并完成
( ) 我已手动更新库存，仅标记完成
(●) 暂不完成

关闭计划标签不会完成计划，也不会改变库存。            [取消] [确认]
```

- 进行中计划可暂停、完成或归档；暂停计划可继续、完成或归档；已完成和已归档计划可重新激活。
- “完成计划”是否显示由当前计划全部目标的合并需求和实际分配结果决定，不能只检查当前展开的模块。
- 点击顶栏“完成计划”和更多菜单中的“标记为完成”进入同一确认流程；确认前都不扣减库存。
- 材料齐备只负责露出顶栏按钮，不显示完成横幅、通知或催促状态；用户可以继续保留进行中计划，等待角色或武器实际开放后再完成。
- 存在未保存修改时，确认完成会先保存当前修改，再原子地执行完成操作；保存失败时保持进行中状态和用户输入。
- 暂停、完成、归档和重新激活后关闭操作层，停留在当前计划工作台，并立即更新顶栏状态、总览列表和库存分配。
- 已完成计划保留历史和完成时间；归档计划默认从总览隐藏，但可以在培养计划列表的状态筛选中找到。
- 总览和培养计划列表的计划行在悬浮或键盘聚焦时提供同一状态快捷菜单；涉及库存扣减的“完成”仍进入完整确认流程。

从旧版本首次进入 v1.3.x 时自动检测；用户选择稍后处理后，可从“设置 > 方案与备份 > 建立全局库存”再次进入：

### 共用边界状态

| 状态 | 界面要求 |
| --- | --- |
| 加载中 | 保持固定布局骨架，不让按钮和表格跳动 |
| 无数据 | 说明缺少什么，并提供唯一明确的下一步 |
| 资料缺失 | 标出具体对象/材料，不把需求当作 0 |
| 当前不可获取 | 计入需求与缺口，但不生成开放日或刷取建议 |
| 计算失败 | 保留用户输入，显示可重试信息，不写入错误结果 |
| 保存失败 | 保留未保存状态，不显示“已保存” |
| 导入失败 | 不替换原数据，并指向校验详情或备份 |

## 视觉、文案与动效

- 基底使用不带绿色倾向的中性冷白与中性灰，交互主色使用克制的灰蓝，少量鎏金用于重点和稀有度；绿色只表示成功、已满足或库存充足。
- 深色主题使用无色相倾向的中性深灰作为基底，保持灰蓝交互色和鎏金重点；浅色与深色采用同一套语义 token，不分别维护页面级颜色。
- 先定义颜色、间距、圆角、边框、阴影、字号、层级与动效 token，再实现共享按钮、Tab、表格、输入、详情查看器、弹窗和通知样式。
- 使用现代、简洁、准确的书面语，例如“今日开放”“明日开放”“尚缺”；不使用“今日可刷”等口语，也不使用“本日”“翌日”等刻意文言表达。
- v1.1.0 替换默认 Electron 图标，统一产品显示名、EXE 名称和 Windows 多尺寸 `.ico`。

### 自动化测试体系

v1.1.0 将测试拆成职责明确的层次，并提供统一验证命令：

```text
npm run test:unit       领域计算、Schema、资料适配和纯函数
npm run test:component  React 组件、表单、弹层和键盘交互
npm run test:integration IPC、文件读写、迁移、备份和失败回退
npm run test:e2e        Playwright 启动真实 Electron 并执行用户流程
npm run test:e2e:headed 仅在明确需要调试时显示 Electron 测试窗口
npm run test:visual     固定窗口与资料下的关键页面截图对比
npm run test:coverage   单元、组件和集成测试覆盖率
npm run verify          lint、测试、类型检查和生产构建总入口
```

- 继续使用 Vitest。将领域和主进程测试放在 Node 环境，将 React 组件测试放在 jsdom 环境，避免所有测试共用错误的运行环境。
- 使用 Playwright 的 Electron 驱动启动发布候选构建，通过可访问名称定位控件并完成点击、输入、标签切换、保存、关闭和重新打开；普通 `npm run dev` 不承担自动验收职责。
- 默认 E2E 以隐藏测试窗口运行，不抢占前台焦点，不移动系统鼠标，也不向真实桌面发送键盘输入；Playwright 在页面内部派发交互事件。
- `test:e2e:headed` 是唯一主动显示测试窗口的调试入口，不进入默认 `verify`。执行前明确告知用户，关闭后不得遗留 Electron 进程。
- E2E 使用临时 `userData` 目录和确定性资料 fixture，不读取或修改开发者及用户的真实 Profile、游戏资料、备份和设置。
- `v1.1.0` 首批 E2E 覆盖打开和切换现有方案、保存与另存为、手动计算、资料更新失败回退及应用重启后的持久化；后续版本再随完整培养计划和库存功能补充新建、恢复、自动命名、重名与库存调整场景。
- 关键页面按固定窗口尺寸保存截图基线。截图差异由测试报告展示，更新基线必须对应已经确认的设计变更。
- 视觉基线保存在本地且不纳入版本控制；README 正式截图作为文档资产纳入版本控制。E2E 失败截图、diff、trace、视频和报告统一进入 Git 忽略的 `out/test-results/`，在下次运行前清理，成功运行后不保留临时诊断产物。
- 每次 E2E 的临时 `userData` 使用系统临时目录中的独立随机子目录。清理顺序固定为关闭 Electron 与子进程、验证目标目录归属、有限重试定向删除；禁止把真实用户目录、仓库根目录或共享目录作为递归清理目标。
- 单元、组件和集成测试合并统计业务源码覆盖率，statements、branches、functions 和 lines 四项均以 90% 为 `v1.1.0` 门槛；不得靠排除核心模块或用 E2E 执行数据虚增结果，达到后采用只升不降规则。
- GitHub Actions 在 Windows 上执行 `npm run verify` 和 Electron E2E；失败时保存测试报告、截图差异和必要日志作为构建制品。
- 系统文件选择器和 Windows 权限提示通过测试适配器验证业务流程；需要真实窗口捕获或系统输入驱动的测试只在专用 Windows CI、虚拟机或用户明确同意的测试环境执行，不在日常本地验证中控制用户桌面。
- 自动化测试以设计文档中的控件、状态和业务结果为断言，不只验证页面能够渲染或按钮能够点击。

```text
读取官方新闻 -> 识别版本号与发布日期 -> 与推算日历比较
             -> 生成校正预览 -> 用户确认或自动校验 -> 更新版本日历

游戏版本 8.x  推算日期 20xx-xx-xx   官方日期 20xx-xx-xx   相差 0 天
活动祈愿阶段  上半 21 天 / 下半 21 天
资料来源       原神官方网站新闻                              [查看来源]
```

- 只从配置并校验过的原神官方网站入口获取新闻；解析结果保留原始 URL、页面发布时间、识别出的版本号和发布日期。
- 官方日期与推算一致时将该日期提升为新的确认锚点；不一致时生成校正记录，并从校正后的日期重新推算后续 42 天周期。
- 页面结构变化、版本号无法唯一识别或日期冲突时保留现有日历，并在游戏资料页提示人工确认。
- 官方日历同步属于游戏资料更新，不与 OCR 背包扫描绑定，也不阻塞离线使用内置日历。

## v3.x.x 及以后

### 角色与武器资料增强

- 展示角色技能说明、各天赋等级数值、武器特效和各精炼等级效果，并标明资料适用的游戏版本。
- 关键等级参考作为辅助信息，不把主观强度结论作为唯一答案。
- 当前版本尚不能获取的材料明确显示资料版本与开放状态。

### 非树脂资源规划

- v3.1.x 起提供材料来源、外部地图入口、地区特产提示和刷新周期，并将探索派遣、锻造和矿石生产天数纳入养成计算。
- 这些功能扩展养成计划对非树脂资源的覆盖，不改变 v1.x.x 已有的材料需求结果。

### 角色资料库

- v4.0.x 建立独立资料库入口，提供角色概览、背景故事、立绘、语音和养成材料。
- 图片、剧情文本和语音受版权与分发许可约束；未确认授权时只提供官方来源或用户主动导入。
- 大图和音频使用可选媒体包，不进入核心绿色 ZIP。

### 跨设备同步与移动端

- 同步对象是 Profile、库存、计划、优先级和设置；游戏资料包由各设备独立维护。
- 离线修改必须可用，冲突不得静默覆盖；库存冲突不能简单相加。
- v2.x.x-v3.x.x 先完善稳定 ID、备份和变更记录；v4.1.x 起实现并验证 WebDAV、云盘或账号服务。
- v5.x.x 在同步方案稳定后进入移动端，桌面端与移动端共享领域规则和 Schema。
- Electron 不能直接生成 Android APK。移动端优先评估 React Native + 共享 TypeScript 领域库，也可比较 Flutter 与 Capacitor；当前不重写桌面技术栈。

## 仍需在详细设计中锁定的少量决策

以下问题不再阻塞 Roadmap，但必须在对应版本的 `DESIGN_vX.Y.Z.md` 中确定：

1. v1.2.x 完成度的具体加权公式。
2. v1.2.x 周本转换的默认推荐方式和确认交互细节。
3. v1.3.x 同优先级计划的默认排序是用户顺序优先还是目标日期优先。
4. v1.4.x 限时开放机制的官方名称、准确期限、服务器时间边界和可靠资料来源。
5. v1.5.x 可接受的掉落率资料来源与最低样本阈值。
6. v2.0.x 本地账号的识别字段、删除恢复和单账号数据迁移细节。
7. v2.1.x OCR 首批支持的背包页面与截图尺寸范围。
8. v2.2.x 的窗口捕获 API、页面定位特征和各显示模式兼容范围。
9. v2.3.x 的输入驱动方式、原生 helper 技术栈、安全停止协议及游戏服务条款调研结论。
10. 移动端立项前的数据同步后端与冲突产品方案。

## 原型与设计协作

- 当前字符原型用于确定信息架构、字段和状态。
- 每个版本开发前，从本 Roadmap 生成 `docs/DESIGN_vX.Y.Z.md`，再制作可点击原型或高保真视觉稿。
- Figma 适合高保真与交互交付；FigJam/Miro 适合流程，Excalidraw 适合快速讨论，Storybook 用于实现后的组件状态验证。
- AI 生成图只适合品牌氛围和图标方向，不作为复杂业务界面的唯一规格。
